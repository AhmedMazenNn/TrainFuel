# Progress API and browser behavior

Milestone 5 adds `weight_entry`, `progress_photo`, and `reminder` sync adapters. Use authenticated session/CSRF requests and the existing `/api/sync/devices/`, `/push/`, `/changes/`, `/snapshot/`, and `/ack/` contract. Mutations go through sync envelopes for both online and offline editors: stable UUID entity/idempotency key, action create/update/delete, base revision (0 for creation), complete editable payload. Deletes use an empty payload. `GET /api/progress/weights/`, `/photos/`, `/reminders/` expose owner-only paginated lists (`offset`, `limit` 1–100).

Weight payload: `{local_date:"2026-10-05",weight_kg:"80.125",notes:""}`. Positive decimals are persisted with three decimal places in kilograms. One active observation per date is the provisional PRD default. Same-date concurrent creation returns `date_already_recorded`, preserves the losing draft, and requires explicit correction; no automatic overwrite. Unit changes affect display/input only. Editing notes without altering the displayed input preserves the exact stored value. Chart segments connect adjacent observation dates only; numeric history is available.

Photo payload: `{week_start:"2026-10-05",capture_date:"2026-10-06",asset_id:UUID,label:"Front",notes:""}`. Monday–Sunday is the provisional default. Capture date and assigned week are separate, editable historical fields; profile timezone never changes them. The asset must be ready, private, owner-held, uploaded for progress, and actively attached to no other domain record. A user-row scope lock followed by the destination week lock serializes allocation and cross-week moves. Slots 1–4, active slot/asset uniqueness, and PostgreSQL checks enforce four accepted photos per week. Replacement retains its slot. A move into a full week fails before changing the original. Replaced/deleted assets receive tombstones and tracked original/thumbnail CleanupTasks; run `cleanup_media` regularly.

Browser photos are staged in owner-partitioned IndexedDB before reporting local success. Sync uploads/processes the file, durably resolves its operation to a stable asset ID before replay, then removes the staged source only after acceptance. `week_full` retains the file and local projection; the sync screen links back to the gallery to change the week, or the user can replace an accepted photo. Failed operations are archived as recovered drafts when explicitly edited. JPEG/PNG/WebP are supported within M2 limits; HEIF and animated progress images are not accepted and remain recoverable. No image conversion is promised without testing.

Private photo cache defaults off. Opt-in keeps thumbnail/original blobs in owner-prefixed IndexedDB metadata (`photo:OWNER:ASSET:VARIANT`), bounded to 50 MiB. It uses authenticated grants, never public/private bearer URLs. Turning caching off, explicit clearing, logout, local deletion, server tombstones, and replacement clear appropriate blobs. Retained queues stay locked to their account. Browser persistence is intended for a trusted device; it is not encryption against someone with browser/devtools access. Cached photos on disconnected devices cannot be remotely erased immediately.

Comparisons offer two weeks, same-label matching with manual choices, wide side-by-side display, narrow labeled toggles, capture dates, available numeric weight observations, and source-preserving original zoom. They work without weight records and make no body-composition claims.

Reminder payload: `{category:"food|exercise|weight|photo",local_time:"09:00",weekdays:[1,3,5],enabled:true}`. ISO days 1–7 must be unique and nonempty. Notification permission is requested only when enabling; denial/unsupported capability leaves all other features available. Scheduling checks every 15 seconds while the page is visible/open, uses the profile timezone for future schedules, and claims owner/reminder/local-minute notification keys transactionally (with browser locks where available). Sync/settings changes do not duplicate the same reminder minute. Generic notification text includes no measurements, food details, photos, or notes. Timers and delivered notification objects are cancelled on account changes/deletion. Browser-closed delivery, email/SMS, and native reminders are not implemented.

## Lifecycle integration

`progress.lifecycle.export_data(user)` provides JSON weight/photo/reminder metadata including asset IDs, without file keys/bytes/URLs. Root lifecycle code separately handles explicitly opted-in photo export. `erase_data(user)` must run inside the account deletion transaction: scrub values/notes/dates, disable reminders, release claims, increment revisions and emit tombstones. Root deactivates the account, revokes sessions, and queues all owned private assets for file cleanup. UUID/FK tombstones and sanitized receipts/feed identifiers remain for stale-replay protection; original personal measurement/notes values do not. Backup expiry and offline-device cleanup depend on release lifecycle configuration, not instant global deletion.
